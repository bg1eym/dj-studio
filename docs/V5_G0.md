# 四 Deck 引擎验证（G0）：量出来的数

> 需求里的 G0：先证明「四路播放、装载、独立控制、音频时钟调度、效果资源」在真正的引擎里成立，时序和资源上限能量出来，再谈 P0 / P1。
> 这一页只记**量出来的数和怎么量的**。数字来自 `packaging/macos/smoke_v5.py`（真引擎）和 `tests/test_v5_*.py`（真引擎 + 模拟器）。
>
> **测的是哪台机器**：Linux x86-64 容器（4 核，gcc 13，Mixxx 2.5.6 源码编的 `djstudio-engine`，没有声卡——引擎按自己的时钟出块）。
> **用户的 Mac 还没有量**：CI 在 Apple 芯片的构建机上跑同一份 `smoke_v5.py`，数字在 Release「ci-logs」的 `app-arm64.log` 里；
> 真机（CoreAudio 声卡时钟、扬声器 / 声卡的输出延迟）要用户跑一次 `DJ Studio selftest` 和 `djstudio demo5` 才知道，见 DEVICE_TEST.md。

## Mac 上的数（CI 构建机）

合并到 `main` 后 CI 第一次在 macOS 上编了四 Deck 的引擎，并在 Apple 芯片的构建机（macOS 26，没有真声卡，引擎按自己的时钟出块）上跑了 `smoke_v5.py`
（mac-app 第 54 次运行）。**这是构建机，不是用户的 Mac**：真声卡的实时线程、输出延迟、一小时不掉音，还是要真机跑。

| 量什么 | Mac 构建机 | Linux 测试机 |
|---|---|---|
| 引擎编译（clang，Mixxx 2.5.6 + `djs5/`） | 通过 | 通过（gcc） |
| 能力表和 Python 的对照表 | 一致 | 一致 |
| 四路计划重合的脉冲（带分频的计划） | 最大偏差 **0.6 帧（0.014 ms）** | 0.6–1.1 帧 |
| 对齐那一段每块的处理时间 | 平均 0.12 ms，最大 5.2 ms | 平均 0.11 ms |
| 满负载（四路 AAC 原速 20 秒 + 4 Echo + 4 Reverb + 4 个带分频的处理组） | 平均 **1.39 ms（预算的 12.0%）**，最大 8.2 ms；超过一半预算 3 块，**超过预算 0 块**；没有晚到的控制步，没有欠载 | 平均 13% 左右 |
| Key Lock 开（4 ms 脉冲，128 → 132） | 起点晚 +0.27 ms，能量重心晚 +0.47 ms | 一样 |
| 静音预跑 64 拍（满负载） | 5.0 秒 ≈ 6 倍速 | ≈ 7 倍速 |

那一次运行里冒烟测试有一条没过（「主输出没有过载」）：负载计划里四台 Deck 的推子都是 6，四个小节第 1 拍的脉冲正好叠在一起 = 4 × 0.8 × 0.331 = 1.06，
本身就超过满幅——过载指示是对的，是测试的电平定得太满（Linux 上 MP3 把脉冲的尖削掉了一点才没碰到；用不压缩的 WAV 在 Linux 的真引擎上一样复现：15 个采样）。
负载计划改成推子 4（叠起来 0.54）。

## 结论

| 问题（需求第 14 节列的） | 结论 |
|---|---|
| 原生核心能不能四路同时放 | 能。Mixxx 2.5.6 的核心建 4 台 Deck、各自的 EQ / Filter，同时放、互不影响（A01） |
| 20 ms 的映射 tick 能不能下发带时间戳的计划 | 不走那条路。v5 的调度器在引擎里、每个音频块跑一次，起 / 停和效果的开 / 关落在采样上（见 ENGINE5.md） |
| 每路可以有几个独立效果 | 发送效果（Delay / Echo / Reverb）是引擎里自己的实例，同时 8 个（尾音也算），不占 Mixxx 的效果单元；处理组 8 个 |
| 时间戳队列的接入点 | 音频回调里、Mixxx 处理 Deck 之前的「控制步」+ 之后的「出声」两处（`djstudio_engine.cpp run5`） |
| Key Lock 的延迟怎么补 | **没补**。见下面「Key Lock」一节：量到的数和以前的对不上，所以只提示、不宣称已补偿 |
| 分频怎么重建 | 线性相位 FIR、三段相加 = 输入的纯延迟（264 帧 @44.1 kHz）；所有的路统一延迟这么多（ENGINE5.md 第 3 节） |
| 效果的历史状态重建要多久 | 静音预跑：满负载时约 7 倍速（见下） |

## 时序

| 量什么 | 结果 | 怎么量 |
|---|---|---|
| 四台 Deck 计划重合的脉冲（四首不同速度 128 / 130 / 132 / 126 BPM、不同相位，统一到 132） | 最大偏差 **0.6–1.1 帧（0.014–0.025 ms）**（几次运行的范围）；验收要求 ≤ 5 ms（A06） | 真引擎 20 倍速录主输出，量每一拍四个脉冲叠成的那一下落在第几帧；同时确认叠出来的峰值是单个的四倍 |
| 起播的时刻 | 落在计划的那一帧（±1 帧）；Deck 提前 4 个块预卷，门在那一帧全开 | 同上；`test_four_decks_start_together…` |
| 同一拍的一批动作 | 同一个音频块里生效；门 / 推子 / 发送的开关在同一帧 | `test_v5_engine.py`（A05） |
| loop 转 100 圈 | 每一圈的起点和全场拍的差 < 1 帧，不累积（A03） | 1 拍的 loop，模拟器 + 真引擎 |
| 132 → 134 → 136 变速、60 分钟 | 全场拍和音频帧数的关系不漂（差 < 1 帧）（A04） | 模拟器 60 分钟；真引擎按片段核对 `phase_ms`（≈ 0.02 ms） |
| 用到分频的计划 | 输出整体晚 264 帧 = 5.99 ms（引擎报 `latency`），四路仍然对齐 | `smoke_v5.py`：带 HIGH 频段 Trans 的计划 |
| Roll 的每一遍（1 拍 → 1/2 拍）| 起点对在格子上，最大偏差 **0.9 帧**；每一遍第一下是满幅（淡化在格点之前走完） | 真引擎 20 倍速录音，量 24 个起点 |
| 分频器「各段不动」时进组 vs 直通 | 残差 **−166 dBFS**（白噪声）/ **−171 dBFS**（扫频），输入 −12 dBFS RMS；验收要求 ≤ −60 dBFS（A14） | `test_insert_bypass_is_the_same_signal…`（模拟器，逐采样相减） |

## 资源

预算：一个块 512 帧 = 11.61 ms。

| 负载 | 每块处理时间 | 说明 |
|---|---|---|
| 四路（WAV）+ loop + 一个 Delay + 一个带分频的处理组 + Roll + 采样 | 平均 **0.11 ms**（预算的 1%） | 20 倍速离线 |
| 四路 **MP3 320k** 原速 + 4 个 Echo + 4 个 Reverb + 4 个带分频的处理组（每组 Trans + Phaser） | 平均 **1.5 ms（预算的 13%）**，最大 3.9 ms；超过一半预算的块 0 个，超过预算的 0 个 | 15 秒，1292 块；没有晚到的控制步，没有重复的回执 |
| 静音预跑（上面那个满负载） | 64 拍（29 秒的音乐）用 4.3 秒 ≈ **7 倍速**，含装载四首 | 所以上限 256 拍的预跑最坏约 17 秒；普通的尾音只要回算几拍 |

### 60 分钟（A18）

| 跑法 | 结果 |
|---|---|
| 真引擎，上面那个满负载（四路 MP3 在 64 小节里循环 + 4 Echo + 4 Reverb + 4 个带分频的处理组），原速 **3600 秒** | 310 087 块；平均 1.60 ms（13.7%）；**没有崩溃、没有晚到的控制步、没有重复的回执、四台 Deck 的相位差一直是 0.000 ms、主输出没过载**。但有 **36 块超过了预算**（最长的一块 119 ms），164 块超过一半预算 |
| 同样的负载，机器空着的时候跑 540 秒 | 46 526 块；平均 1.56 ms（13.5%）；2 块超过预算（最长 36 ms），11 块超过一半 |

怎么读这两行：60 分钟那一轮跑的时候，同一台机器还在编译引擎、跑另外两轮全量测试，所以它只说明「一小时不崩、不漂、不重复」，**不能当「没有欠载」的证据**。
机器空着时还是偶尔有一块被打断——这台测试机是共享的虚拟机，处理音频的线程没有实时优先级，也没有声卡在拉时钟；这种单块的停顿是处理线程被系统挂起，
量到的时间里 Mixxx 的 Deck 处理和 v5 的混音分不开。**在 Mac 上（CoreAudio 的实时线程）会不会有，要真机跑 `smoke_v5.py --long 3600` 才知道**；平均负载（13% 左右）说明算力是够的。
另外没量的一项：音频线程和主线程共用一把锁（主线程每 50 ms 取一次状态、收回执），锁的等待时间没有单独统计。

判定看的是平均值和「超过预算的块数」，不是单看最大值。

## Key Lock

| 量法 | 结果 |
|---|---|
| v5，4 ms 的脉冲，素材 128 BPM 放在 132（速率 1.031），Key Lock 开 | 脉冲的起点比计划晚 **+0.27 ms**（0.15–0.39），能量重心比不开时晚 **+0.47 ms** |
| 同上，Key Lock 关 | 0.00 ms（−0.01 … +0.02） |
| 以前（v4，合成 kick，两首叠着听起音间隔，见 MIXXX_NOTES.md） | 晚 17–29 ms |

两组数对不上：脉冲很短，变速器（RubberBand）对它几乎不抹；kick 这种带低频长尾的声音以前量到的要大得多，在 v5 里还没有重新量。
所以现在的处理是：默认关（和 v4 一样）；谱里开了 Key Lock 的片段编译时给一条提示；能力表里 `keylock_compensated: false`。**没有做延迟补偿，也不宣称 A06 里「Key Lock 开」的那一半已经达标。**

## 没有做的 / 只做了一部分的

- **采样率和块大小的组合**：引擎固定 44.1 kHz / 512 帧。需求里的 48 kHz、256 帧没有做（引擎的输出格式是写死的，Mac 的声卡是 48 kHz 时由系统重采样，和 v4 一样）。分频器本身在 48 kHz 下的检查跑过（延迟 288 帧 = 6.0 ms）。
- **Mac 上的数**：见最上面。
- **60 分钟稳定性（A18）**：真引擎满负载跑满了 60 分钟（不崩、不漂、不重复），但不是在干净的机器 / 真声卡上，「没有欠载」这一条没有证据，见上面「60 分钟」。P0 的「四路 + 四 Echo + 四 Reverb」和 P1 的处理组是合在一起跑的，没有分开各跑 60 分钟。
- **检查点缓存**：从中间开始每次都重新预跑，没有缓存。
